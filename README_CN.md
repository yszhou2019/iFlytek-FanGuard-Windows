# FanGuard

给不正常的 Windows 进程加一个「CPU 上限」。

[English version → README.md](README.md)

---

## 为什么要做这个东西

这个项目是为一件非常具体、非常烦人的事情写的：**讯飞输入法在 Windows 上的使用体验**。
同一个产品有三个问题，而且因为它是闭源软件，用户一个都改不了。

### 问题一：长语音经常意外断开

在「长语音模式」下你可以连续说话、文字持续上屏。但实际使用中，长句子经常中断并弹出：

```
网络故障，请重新输入
```

短句通常没问题，长句经常不行。这不是用户侧的网络问题 —— 抓包显示连接本身非常健康
（建连约 0.2 秒、TLS 约 0.1 秒、上传约 417 KB/s、零重传、且未走代理）。在每一次失败的会话里，
都是**本机客户端先发出 FIN**，也就是讯飞客户端或它的账号/会话层在中途主动放弃了。
重装、重启、换 DNS、关防火墙、开日志级别，全都没有改变结果。这是厂商侧的缺陷。

### 问题二：离线模式识别不准

最直接的替代方案是离线识别，但本地模型的准确率明显不如在线模型，没法当作听写的替代品。

### 问题三：唯一好用的那条路，会白白吃掉一个 CPU 核心

真正可用的方案是：**在手机上说话**，再用讯飞的「跨屏输入」把识别好的文字发到 Windows。
此时电脑只是一个**接收端**。

这个功能在 Windows 侧的进程是：

```
C:\install\iFlytek\iFlyIME\3.0.1750\iFlyIMEConnector.exe     （32 位）
```

任务管理器里显示为 **跨屏输入(32bit)**。而它会**长期占用约 100% 的单个核心**，同时：

* 网络 IO 为 **0 字节/秒**，
* 磁盘 IO 几乎为 0，
* 并且它没有在做任何有意义的工作。

最后这一点是关键。所有真正耗算力的部分（声学模型、语言模型、解码）都发生在**手机端或云端**。
Windows 这个进程只负责接收已经识别好的文字再转发出去。一个只收几个字节文本的进程，
没有任何理由占满一个核心 —— 所以它烧掉的 CPU 是**纯粹的浪费**，几乎可以确定是闭源代码里
一个 busy-wait / 空转循环的 bug，而我们打不到这份代码。

实际的后果就是噪音：笔记本风扇一旦转起来就再也不停，哪怕你根本没有在说话。

### 那我们能做什么

厂商的代码我们改不了，我们也不想自己造一个输入法去替代它。但我们可以控制
**操作系统允许这个进程使用多少 CPU**。既然已经证明它是在空转，那么把 CPU 收回来
就没有任何代价。

FanGuard 做的就是这一件事：一个外部的、非侵入式的 CPU 上限。

---

## FanGuard 做了什么

FanGuard 通过周期性地挂起 / 恢复目标进程，把它在**任务管理器里显示的 CPU 占用**压到一个
固定值。限制值就是一个普通数字：

```json
"targetCpuPercent": 5
```

控制器会闭环测量真实占用，并不断调整「运行 / 暂停」的比例，直到实测值收敛到目标值。

* 如果进程本来就很闲，FanGuard 会自动退让、不去打扰它。
* 如果进程自己重启了，FanGuard 会自动重新挂上。
* 不注入、不 Hook、不 patch、不修改任何文件 —— 完全从外部通过
  `NtSuspendProcess` / `NtResumeProcess` 实现。
* 它是通用的：把 `processName` 指向任何一个空转进程都可以，不限于讯飞。

## 环境要求

* Windows 10 1809+ 或 Windows 11
* 管理员权限（脚本会自行提权；管理员账号在默认 UAC 设置下不会弹窗）

## 用法

```powershell
# 1. 先改 FanGuard.config.json 里的目标值，然后：
.\FanGuard.ps1 install      # 注册登录自启任务并立即开始限流

.\FanGuard.ps1 status       # 查看任务状态、守护状态、实测 CPU
.\FanGuard.ps1 test         # 跑 20 秒，打印实测 CPU 后退出
.\FanGuard.ps1 uninstall    # 移除任务并恢复全速
```

如果你更喜欢双击，用这两个「一件事专用」的启动器：

```
install.cmd        # 注册登录自启任务并开始限流
uninstall.cmd      # 移除任务并恢复全速
```

两者都会自行申请管理员权限。**在删除或移动本文件夹之前请先运行 `uninstall.cmd`**，
否则计划任务会一直指向一个已经不存在的路径。

其他命令用通用的 `FanGuard.cmd`：

```
FanGuard.cmd status
```

执行 `install` 之后就是全自动的：每次登录自动启动，目标进程重启后自动重新挂上。

## 配置项

`FanGuard.config.json`：

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `processName` | `iFlyIMEConnector` | 要限流的进程名（不带 `.exe`） |
| `targetCpuPercent` | `5` | CPU 上限，就是任务管理器显示的那个数 |
| `periodMs` | `400` | 一个「运行 + 暂停」周期的长度 |
| `minRunMs` / `maxRunMs` | `5` / `380` | 控制器对运行时长的上下限 |
| `initialRunMs` | `40` | 首次测量前的初始运行时长 |
| `controlWindowSec` | `3` | 控制器重新调整的频率 |
| `deadbandPercent` | `1.0` | 小于这个偏差就不调整 |
| `useEfficiencyMode` | `true` | 同时套用 Windows 11 效率模式（12 代及以上 CPU 才有效） |
| `highResTimer` | `true` | 请求 1 ms 定时器精度，让休眠更准确 |
| `taskName` | `FanGuard` | 计划任务名称 |
| `logFile` | `FanGuard.log` | 日志路径（相对脚本目录） |
| `maxLogSizeKb` | `256` | 日志轮转阈值 |

改完配置后重新执行一次 `.\FanGuard.ps1 install`。

## 实现原理

```
每 controlWindowSec 循环一次：
    实测 CPU% = (cpu_now - cpu_prev) / elapsed * 100
    runMs <- clamp(runMs * 目标 / 实测)
    每 periodMs：  恢复 -> 睡 runMs -> 挂起 -> 睡 (periodMs - runMs)
```

因为测量窗口跨越了正常的运行 / 暂停周期，它收敛出来的数字就是任务管理器显示的那个数字。

在 i5-9300H 上对 `iFlyIMEConnector.exe` 的实测结果：

| | CPU |
| --- | --- |
| 不限流 | 101.5 % |
| 目标 5% | 4.6 – 5.6 % |

## 注意事项

* 单靠效率模式（EcoQoS）在没有能效核的 CPU 上**无效**（Intel 9 代及更早）：它依赖把线程
  调度到 E 核。FanGuard 仍会在可行的情况下启用它，但真正到处都管用的是占空比限流。
* 目标值过低（1–3%）会让输入略微变迟钝。如果觉得有黏滞感，把 `targetCpuPercent`
  调到 15–20 再 `install` 一次。
* 受 Windows 定时器粒度限制，实际可达下限大约是 3–4%，1–2% 无法稳定达到。
